# MicroWIN SMART 梯形图编写与原生验收

## 已证实的失败：独立逻辑挤在一个 Network

2026-09-08 的早期快照：一份离线工程在全新 MicroWIN 进程中编译为 0 错误，但全部 13 块原生 LAD 打印输出的 136 页中有 36 个无效程序段。35 段包含多条独立逻辑；另 1 段是布尔能流参数 CALL 简写；随后官方《子例程调用示例》明确说明此种简写只能显示为 STL，须按保留 L 区展开。当时只验证了原 SBR8 N3 拆分后的代表段，不能据此宣称整份工程通过。

同日后续最终记录已经关闭该修复版的离线验收：13 块可导出内容往返一致，298 个可见段/162 页 LAD 完成浏览，并有保存重开、全新进程编译和重印证据。证据为 项目内部保存的离线验收记录（不包含在本公开技能中）。此历史结果不适用于其他文件或后续修改，也不是现场验收；旧窗口 37 个错误 67 的根因仍未查明。

下面是结构示意，符号只是占位名称，不能未经工程核对直接导入：

```text
Network 10
LD Tick
AW< Age, +32767
INCW Age
LDW<> Heartbeat, PreviousHeartbeat
AN FirstScan
MOVW Heartbeat, PreviousHeartbeat
MOVW +0, Age
```

前半段计时，后半段检查新心跳后清零；它们是两条独立逻辑。STL 能执行，不保证 LAD 转换器能在同一段绘制。应把第二条逻辑放到紧随其后的新 Network，保持原先先计时、再检测、再清零的顺序。尤其不能交换多个判断依次覆盖结果码的顺序。

不要把所有第二次 LD 都拆开：LD/ALD/OLD 的嵌套逻辑、LPS/LRD/LPP 的分支栈，以及编译器生成的布尔 CALL 参数连接都可能是一个合法梯形图段的组成部分。只拆已分析为独立的逻辑，并核对边沿存储与局部临时区。

## 参数化库调用：按实际库签名处理

- 同时核对当前工程的库名称、真实 SBR 编号、输入输出签名、符号表和原生导出，不能只看某张符号提示表就认定库编号改变。
- 错误 67（操作数数目与指令签名不匹配）和 LAD 的“无效程序段”是两种证据，必须分别复现。
- 已观察到同一磁盘工程在旧编辑窗口报 37 个错误 67，而全新进程编译 0 错误。旧窗口问题的根因尚未证实；不要宣称重启、切换 LAD 或改成库符号已经根治。
- 对 BOOL 参数，参考该工程中已经能转换的原生同类功能框，并导出其 AWL 连接结构。直接写 `LD enable / CALL block, first,...` 即使编译通过，也未证明可画成 LAD。
- 官方确认 LB60～LB63 保留给调用参数数据；跨 Network 拆分时不能把它们当作稳定的用户状态变量。检查整个调用位置的读写和原生重生成结果；若需新临时变量，先核对占用、生命周期、首扫和扫描顺序。

## 保留受保护库的局部导入

在本机 MicroWIN SMART 已实测：含 OB1 的程序导入会替换程序块集合；省略的受保护库可能丢失。官方导出中的受保护库可能只有声明桩，不能当成可还原库实现的完整源文件。

- 原 SMART、数据块、系统块和符号关系分别备份，使用独立工程副本。
- 只更新普通 SBR 时，导入文件仅含目标 SBR，不附 OB1 或受保护库桩。
- 需要更新 MAIN 时，可先把目标 MAIN 包装成核实未占用的临时 SBR，局部导入后用已在独立副本验证的原生程序段对象操作更新 MAIN，再按批准范围移除临时块。必须区分网络对象操作和文本粘贴；STL 的 OVR 只覆盖字符，不能据此认定整段或整块被替换。见 [native-integration.md](native-integration.md)。
- 每次集成后确认库、全部原 POU、数据块仍存在，再执行编译和官方导出比对。上述导入替换范围同时得到官方《导入》（32196111755）明确支持；其他版本仍应核对对应帮助。

## 原生验收必须覆盖整个交付

1. 静态比对可执行指令、操作数、常量、定时器、边沿位置及覆盖写入顺序；注释/Network 编号变化单独记录。脚本模型测试须写明其模拟边界。
2. 实际导入并完整编译，记录程序、数据和系统块的错误/警告；不能以只编译当前块代替全部编译。
3. 在 LAD 模式检查所有修改段，并检查同一 POU 剩余段。较大工程可从 MicroWIN 将全部程序块打印到本地 PDF，确认打印范围、块名与 Network 覆盖。先选本地 PDF 打印机，避免默认物理打印。
4. 从原生 PDF 查找 `无效程序段`，按“块名 + Network 编号”去重，而不是数词语出现次数。页中可能同时有标题和占位文字。文本无错误词不够，还要核对程序段覆盖，并查看修复页和功能框参数的实际图形。
5. 保存、关闭、重新打开并再次全部编译/查看 LAD。出现窗口状态差异时增加全新进程验证。官方导出再与候选源码和原数据块核对。
6. 只在上述证据完成后写“离线 LAD 验收通过”。现场许可、下载、运行及设备试验是另一阶段，不从离线修复授权推断。

## 避免把尚未验收写成完成

保留失败记录。某次编译成功不能覆盖后来重现的错误；某个代表段成功不能推广为全程序完成。验证受 UI、用户输入或工具阻碍时，精确写出已完成和未完成部分，不用“已修复”代替未取得的原生证据。
